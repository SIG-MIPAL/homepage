# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A **single-repo, multi-page** data-driven setup. The **MIPAL lab site** is the entry page
(`index.html` at repo root); each lab member can have a **self-contained personal page** under
`people/<slug>/` (profile + customizable sections: news / education / publications / awards /
text / links). All pages are static, baked from their own `content.json`, and deployed together
from `master` via GitHub Pages (`git@github.com:XunCHN/Homepage.git`, live on the git.io URL).
A **local-only Node.js admin** (`admin/`) edits any page with a live preview, creates/deletes
member pages, and publishes everything in one click. Nothing is deployed to a server - the admin
is a local dev tool; only the static frontends are served by GitHub Pages.

## Architecture

```
Homepage_v2/  (ONE repo, master -> GitHub Pages root)
├── index.html        # MIPAL (entry) - GENERATED by `node admin/build.js mipal`, do not hand-edit
├── content.json      # MIPAL source of truth
├── style.css  site.js  images/   # MIPAL assets
├── people/<slug>/    # a member personal page (self-contained, base="") - one folder per member
│   ├── index.html    # GENERATED by `node admin/build.js <slug>`
│   ├── content.json  # that member's source of truth (section-driven)
│   ├── style.css  site.js  images/   # style.css + site.js copied from admin/tpl at build time
├── .nojekyll  .gitignore  CLAUDE.md  google6e027989c2c8311c.html
└── admin/            # LOCAL editing backend (gitignored - never pushed; OneDrive backs it up)
    ├── sites.js      # site registry: mipal->repo root + dynamic scan of people/<slug>/
    ├── render.js     # personal renderer (section-driven); exports renderHTML, esc, renderAuthors, renderPub
    ├── lab-render.js # MIPAL renderer; reuses esc + renderPub from render.js
    ├── build.js      # node build.js [key]  -> writes <siteRoot>/index.html (default = mipal)
    ├── server.js     # Express: ?site= for content/draft/images/preview; create/delete member pages; publish rebuilds ALL
    ├── tpl/          # style.css + site.js template - single style source, copied into every member page at build
    ├── admin.html/.css/.js  # editor UI (site switcher + per-site tabs + resizable live preview)
    └── package.json    # dep: express
```

**Key invariant:** every `index.html` is generated. To change content, edit that page's
`content.json` (via the admin or directly) then rebuild. Never hand-edit `index.html` - the next
publish overwrites it.

**Renderers:** `render.js` (personal pages) and `lab-render.js` (MIPAL) each export
`renderHTML(content, {base})`. `base` is `""` for the baked/deployed page and `/site/<key>/`
for the live preview (so preview assets resolve through the server's per-site static mount).
`render.js` is **section-driven**: it renders `content.sections` (type pool + enabled/title/order)
plus the always-on profile block; empty sections are hidden. `lab-render.js` reuses `esc` and
`renderPub` from `render.js`, so publications render identically on every page.

**Site registry** (`admin/sites.js`): `mipal` -> `Homepage_v2/` (default, static); each
`people/<slug>/` with a `content.json` is discovered dynamically as a personal site
(`key = slug`, `type = 'personal'`, `memberType` from `content.member.type`). `getSites()` scans
on demand, so pages created at runtime are visible immediately. `build.js` and `server.js` both
consume it.

**Why member pages are self-contained** (own `style.css`/`site.js`/`images`, `base=""`): the
live-preview system serves each site root at `/site/<key>/` and renders with that base. A
self-contained sub-folder works for both deployed (`base=""`) and preview (`base="/site/<slug>/"`)
with zero changes to the renderers; sharing root assets via `base="../"` would break the preview
mount. The asset duplication is bounded by keeping a **single style source** in `admin/tpl/`:
`build.js` re-copies `tpl/style.css` + `tpl/site.js` into every member page on each build, so all
pages stay in sync without hand-editing each copy.

**Member links (dual mode):** on the MIPAL People tab, each member has an optional `homepage`
(external URL) and an optional `page` (a local `people/<slug>` slug). The "Web" link resolves to
`homepage` if set, otherwise to `people/<slug>/index.html` (base-prefixed). So a member either
links to a third-party profile or to their local page - never both.

**Backend locality:** `admin/` is gitignored, so `git push` carries only the page files (root +
`people/*/`). The repo lives inside OneDrive, so the gitignored `admin/` is still synced/backed
up locally.

**Publish** rebuilds **all** pages (MIPAL + every `people/<slug>/`) then does a single
`git add -A && commit && push` in the repo root - one push deploys everything.

## Common commands

```powershell
# Run the admin editor (one-time install, then start) - or just double-click admin/start.bat
cd admin; npm install
cd admin; npm start            # -> http://localhost:3000  (use the site dropdown to switch pages)

# Rebuild a page's index.html from its content.json (without the admin UI)
node admin/build.js            # mipal (default) -> root index.html
node admin/build.js <slug>     # a member page -> people/<slug>/index.html

# Verify the admin server + sites
Invoke-RestMethod http://localhost:3000/api/sites -UseBasicParsing
```

There is no lint or test suite.

## Editing workflow

1. `cd admin; npm start` (or double-click `admin/start.bat`), open http://localhost:3000.
2. Pick the page in the **top-left dropdown**, grouped into **Lab** (MIPAL) and **People**
   (each member). MIPAL is the default. Switching discards unsaved edits in the current page
   (with confirmation).
3. **+ New page** (top bar) creates a member personal page: enter a name + member type
   (faculty/phd/master/visiting). This lays down `people/<slug>/` with starter content AND adds
   a record to the MIPAL People list (in that type's group) so the member appears on the lab
   page with "Web" pointing to the new local page. **Delete** (top bar, member pages only)
   removes both.
4. Edit in the tabbed UI. The right-hand pane is a **live preview** that updates ~450ms after
   each edit (it posts an in-memory, per-site draft to the server; drafts are NOT written to
   disk and do not bleed across pages). **Drag the splitter** between editor and preview to
   resize (position is remembered); **↗ Open in new tab** pops the preview into its own tab.
5. **Save** writes the current page's `content.json` to disk.
6. **Publish to GitHub** rebuilds **all** pages, then `git add -A && commit && push` to
   `master` once. Everything goes live on the git.io URL (MIPAL at root, members at
   `/people/<slug>/`).

Tabs: MIPAL = Home / News / People / Publications / Resources / Contact / Meta.
Member page = Profile / Sections / News / Education / Publications / Awards / Meta.
The **Sections** tab controls which blocks show on a member page: toggle Show, edit the Title,
reorder, and add custom `text`/`links` blocks. Standard types (news/education/publications/awards)
pull content from their own tab. News, Publications, and Meta editors are shared.

## MIPAL content.json schema (root)

- `meta` - title, description, keywords, favicon, last_updated
- `home` - `lab_name` (short, in nav), `full_name`, `affiliation`, `hero_image?`,
  `intro[]` (HTML allowed), `highlights[]`, `cta_links[]` (`{label,url}`)
- `nav` - section ids (home, news, people, publications, resources, contact)
- `news[]` - `{date, text}` (shared shape)
- `people` - `{faculty, phd, master, visiting}`, each a list of members:
  `{name, role, photo, homepage?, page?, scholar?, github?, email?, note?}`. Empty groups are
  hidden. (`faculty` = Faculty & Guest Faculty; the `role` field distinguishes them.)
  `homepage` = external URL (wins for the "Web" link); `page` = local `people/<slug>` slug
  (used when `homepage` is empty). The PI's record has `page: "xun-jiang"`.
- `publications` - `{journals, conferences}` (identical to the personal schema)
- `resources[]` - `{title, desc, type, url}` where type ∈ Dataset/Code/Demo/Course/Other
- `contact` - `pi_name`, `pi_email`, `address[]`, `email`, `map_src?` (Google Maps embed src),
  `links[]`

Member page content.json schema: `meta`, `profile` (name/photo/tagline/bio[]/email/links[]),
`member` (`{slug, type}` where type ∈ faculty/phd/master/visiting), `sections[]`
(`{id, type, title, enabled}` - type ∈ news/education/publications/awards/text/links; order =
display order; empty sections are hidden), plus the content arrays
`news[]`, `education[]` (logo/period/institution/details[] where detail is a string or `{note}`),
`publications.{journals,conferences}[]`, `awards[]`. `text`/`links` sections carry their content
inline in `section.items`. Publication author flags: `self` (bold), `equal` (`*`),
`corresponding` (`#`); a trailing note is added automatically.

## Gotchas

- **Unicode**: editing through the admin UI preserves UTF-8 (emojis, em/en dashes, `·`).
  Do **not** round-trip `content.json` through PowerShell `ConvertTo-Json`/`Invoke-RestMethod`
  - PS 5.1 mangles non-ASCII bytes. Read/validate JSON with `node -e` instead.
- **Publishing pushes for real** - it commits and pushes to `master` (live on git.io), and
  rebuilds **all** pages first. Save each page's edits before publishing (unsaved admin edits
  are NOT published).
- **Style source is `admin/tpl/`** (`style.css` + `site.js`). `build.js` copies these into every
  member page, so edit the template once and rebuild to restyle all member pages. Do not edit
  `people/<slug>/style.css` directly - the next build overwrites it. The MIPAL root `style.css`
  is separate (lab layout) and is NOT auto-synced with the member template.
- **Member pages are self-contained**: each has its own `images/`. A member's `profile.photo` /
  education logos resolve against `people/<slug>/images/`, while MIPAL People `photo` resolves
  against the root `images/` - they are independent. New member pages start with an empty
  `images/`; upload via the image picker while editing that page. A member's MIPAL People card
  photo starts blank (initial-letter placeholder) - set it separately on the MIPAL People tab.
- `google6e027989c2c8311c.html` (repo root) is a Google Search Console verification file;
  keep its exact name.
- The PI's page lives at `people/xun-jiang/` (migrated from the old `personal/`). The original
  personal page was based on Lei Wang's template (credited in its footer).
- Legacy/unused files from the old template have been removed (`w3.css`, `font-awesome.min.css`,
  `jquery*.js`, `stylesheet.css`, `a2_summary_save_dict_val-line_test_data_list_f80_disentangle.json`).
